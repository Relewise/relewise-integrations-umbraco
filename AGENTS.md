# Repository guidelines

## C# and public contracts

- Inspect nearby implementations and preserve existing conventions. Keep changes focused on the requested behavior.
- Put each top-level class, interface, record, struct and enum in its own file, named after the type. Private nested implementation types may stay at the bottom of their containing type.
- Use four-space indentation, UTF-8, CRLF line endings and a final newline. The DemoStorefront bootstrap view `Views/storefront.cshtml` follows Umbraco's generated format (UTF-8 BOM, no final newline), as scoped in `.editorconfig`. Remove trailing whitespace and unused imports.
- Put control-flow bodies on separate, indented lines. Never put `return`, `continue` or `break` on the same line as its condition. Use braces for multiline bodies and all branches of an `if` with `else`/`else if`.
- Use named arguments for boolean literals and other arguments whose meaning is unclear at the call site, especially consecutive flags.
- Prefer small internal domain collections for shared mapping state when they can own lookup and membership rules; avoid exposing raw dictionaries across architectural boundaries or introducing wrappers without useful behavior.
- Simple method/constructor argument guards may remain on one line; prefer `ArgumentNullException.ThrowIfNull` and similar helpers.
- Group scope ownership, service resolution, input preparation and working state into distinct paragraphs. Declare locals near their first use; avoid consecutive setup blocks that mix these responsibilities. Prefer imports or descriptive type aliases over fully qualified type names in method bodies.
- Separate logical steps with blank lines. Wrap code at 120 columns. Expand long calls and signatures with one argument/parameter per line and consistent continuation indentation; keep short calls compact. Wrap long string content without changing its value. Expand enum members and empty constructors onto separate lines.
- Every C# type must belong to a namespace matching the project root namespace plus its physical folders. This is mandatory across the repository, not only in the sample. Prefer file-scoped namespaces. Use `var` only when the initializer makes the type obvious, such as an explicit constructor, cast, literal or generic call naming the returned type. Otherwise write the type explicitly, including for built-in types returned by indexers, properties and method calls. Follow `.editorconfig` for target-typed construction and formatting.
- Keep using directives outside namespaces, sorted with `System` first, followed by other namespaces, static imports and aliases; do not add blank import groups. Apply ReSharper's Adjust Namespaces / Optimize Usings or the shared `dotnet format` rules before delivery. Namespace and import checks must pass in CI.
- Name cancellation parameters `token` and put `CancellationToken` last in every signature, including internal helpers and test callbacks. Preserve existing public parameter names when renaming would break named-argument callers. Use the solution-wide latest C# language setting.
- ReSharper inspections are local IDE checks and must not run in CI/CD. Keep local inspections free of warnings and errors. Fix real findings rather than disabling inspections. For genuine indirect property usage in presentation contracts and public callback contexts, use the narrow shared `.editorconfig` scopes; do not add per-model JetBrains annotations or dependencies just to silence usage warnings. Keep private-member and application-code inspections enabled. Preserve the shared ReSharper code-style settings.
- Keep the public surface small. Document public contracts with useful XML comments matching the existing package, and preserve compatibility unless a breaking change is explicitly agreed.
- Write every XML `<summary>` with its opening tag, text and closing tag on separate `///` lines, including one-sentence summaries. Preserve inline tags such as `<see>`, `<paramref>` and `<c>` inside the text; self-closing `<inheritdoc/>` comments remain unchanged. Keep this layout when generating or formatting documentation.
- Do not rename existing public members as part of formatting or file organization.
- Use the `Async` suffix for new Task/ValueTask operations. Preserve framework-required names and obsolete compatibility entry points; synchronous configuration and registration methods do not take the suffix.
- Keep integration metadata in `RelewiseDataKeys` and internal runtime names in `Constants`; keep sample schema/business names in `DemoConstants`. Separate source property aliases from exported Data keys, centralize dynamic key construction, and prefer constants owned by the supplying framework when available. Keep single-owner keys near their owner and preserve literal contract expectations in relevant tests.

## Examples, tests and local material

- Keep runnable examples and their mapping/converter implementations centralized in `samples/Relewise.DemoStorefront`. Link guides to those source files rather than adding separate example projects or duplicate implementations. Preserve culture-aware mapping, nested block extraction and legacy compatibility examples when updating the demo.
- Organize the DemoStorefront by feature, with package examples in `Integration`, shared site presentation/context in `Site`, installation in `Setup` and seeded schema/content in `Seeding`. Match namespaces to folders; keep HTTP adapters separate from shopping operations and rendering. Keep Vue components grouped by feature under `Client/src`.
- Render storefront pages and shared presentation in strongly typed Razor views/partials. C# prepares view models and handles application behavior; do not build page markup with HTML strings. Preserve Vue payload contracts and use encoded framework helpers for any small HTML fragments those contracts require.
- Keep credentials, generated Umbraco databases, ad hoc smoke-test tooling and raw execution reports in ignored local files. Do not publish them with the package.
- Keep one backend test project. Group package tests under `Mapping`, `Indexing`, `Search`, `Dashboard`, `Tracking` and `Compatibility`; keep sample tests under `DemoStorefront`. Match namespaces to folders, keep each test class focused on one responsibility, and extract shared setup only when multiple test classes need it.
- Keep permanent backend tests focused on observable behavior, regressions and compatibility. The DemoStorefront deliberately has no frontend test suite; verify its UI in a browser. Build affected projects and run relevant backend tests after code changes.
- Build the dashboard with `npm run build` in `src/Integrations.Umbraco/Client` when changing frontend code.
